## مرحله ۶ — گزارش XLSX و HTML چاپی ✅

### چه ساخته شد

| مورد | توضیح |
|---|---|
| `Core\ReportWriter.cs` | **جدید** — نویسنده XLSX (OpenXML خام) و HTML، **بدون هیچ پکیج خارجی** |
| دو دکمه جدید | «خروجی Excel» و «گزارش چاپی (HTML)» در تب گزارش‌ها |
| `DatabaseService.ExportXlsx()` / `ExportHtml()` | تولید گزارش با سرستون‌های ترجمه‌شده |
| `LocalizeColumns()` | نام ستون‌های SQL → عنوان ترجمه‌شده (گرید، CSV، XLSX و HTML یکسان) |
| سرستون CSV | حالا پویا از خود DataTable ساخته می‌شود (قبلاً لیست ثابت و ناهمخوان بود) |
| `--export <csv\|xlsx\|html>` | مسیر headless برای زمان‌بندی و تست خودکار |
| ۲۴ کلید ترجمه جدید | مجموع به **۹۲ کلید** رسید |

**چرا XLSX خام؟** افزودن پکیج‌هایی مثل ClosedXML یا OOXML، حجم برنامه را زیاد و حالت portable را
شکننده می‌کند. XLSX در واقع یک ZIP با چند فایل XML است؛ پس بدون وابستگی ساخته می‌شود.

**چرا HTML به‌جای PDF؟** PDF فارسی نیازمند فونت و shaping است و یک وابستگی سنگین (ده‌ها مگابایت)
می‌آورد. گزارش HTML یک فایل خودبسنده است و با «Print → Save as PDF» مرورگر به PDF تبدیل می‌شود.

ترتیب بازیابی: فایل زبان درخواستی → فایل انگلیسی → خودِ کلید. پس فایل خراب هیچ‌وقت برنامه را نمی‌شکند.

### دو اشتباه در اسکریپت که گرفته و تعمیر شد

اسکریپت تبدیل، ۴۷ رشته را جابه‌جا کرد اما در دو جا خطا داشت — و هر دو **قبل از پذیرش** پیدا شد:

1. **آفست شماره خط:** درج `xmlns:loc` پیش از پردازش، همه خطوط را یک واحد جلو برد و هر ۴۲ هدف شکست خورد.
   (اسکریپت در صورت شکست چیزی نمی‌نویسد، پس فایلی خراب نشد.)
2. **یک الگوی regex و ۴ مقدار فارسی:** الگوی زیرنویس سربرگ، بخشی از متن اصلی را هم در گروه捕获
   گذاشت و نتیجه `Text="Portable Instagram {loc:Text ...}"` شد؛ و استخراج مقدار فارسی برای ۴ کلید،
   نام کنترل را هم برداشت. هر دو تعمیر و مجدداً تأیید شدند.

این دقیقاً همان دلیلی است که پروتکل «تست واقعی + تأیید بصری» قبل از اعلام اتمام اجرا می‌شود.

## 🔴 باگ بحرانی که در همین مرحله کشف و رفع شد — کهنه‌بودن پشتیبان در حالت WAL

### چطور کشف شد
مقایسه پشتیبان مرحله ۲ با دیتابیس زنده نشان داد پشتیبان **اسکیمای نسخه ۰** دارد در حالی که دیتابیس زنده نسخه ۲ است. این تفاوت به‌جای نادیده‌گرفتن، ریشه‌یابی شد.

### ریشه
```
database.db       (فایل اصلی — هنوز اسکیمای قدیمی)
database.db-wal   (۴۱ KB — همه تغییرات جدید اینجا)
```
پس از مهاجرت فاز ۲، برنامه با `Stop-Process -Force` بسته شد → SQLite **WAL را چک‌پوینت نکرد** → فایل اصلی قدیمی ماند.
`BackupService.Create()` فقط `database.db` را کپی می‌کرد → **پشتیبان بدون آخرین داده‌ها**.

### اثبات قطعی (تست بازسازی سناریو)
| مرحله | نتیجه |
|---|---|
| ساخت حالت WAL-only با قطع ناگهانی | `database.db-wal` = ۵۳٬۵۹۲ بایت |
| SQLite مارکر را می‌بیند | ✅ ۱ |
| **کپی ساده `database.db` (روش قدیمی)** | ❌ **۰** → پشتیبان کهنه |
| **پشتیبان با کد اصلاح‌شده** | ✅ **۱**، schema v2، ۴ کمپین |

### اصلاح ریشه‌ای
1. **`CreateConsistentSnapshot`** — به‌جای کپی فایل، `VACUUM INTO` از خود SQLite درخواست یک نسخه تراکنشی‌سازگار می‌کند.
2. **Fallback** — اگر `VACUUM INTO` ممکن نبود: `PRAGMA wal_checkpoint(TRUNCATE)` سپس کپی.
3. **بازیابی** — اگر پشتیبان قدیمی حاوی `-wal` باشد، آن هم منتقل می‌شود (وگرنه داده از دست می‌رفت).
4. **خودترمیمی در استارتاپ** — `wal_checkpoint(TRUNCATE)` در `RunStartupMaintenance` تا حتی کپی دستی کاربر از `database.db` هم کامل باشد.
5. **`--backup` headless** — برای زمان‌بندی با Task Scheduler و تست خودکار.
